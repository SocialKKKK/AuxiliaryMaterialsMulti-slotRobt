# 开发环境准备（本机 / 笔记本）

> 适用对象：在**个人笔记本**上开发 `wire-cabinet` 的开发者，机器不在厂区网络、没有现场硬件。
> 现场联调所需的外部条件另见 [../docs/开发待补齐信息.md](../docs/开发待补齐信息.md) §3（P1–P8）。

---

## 1. 一次性准备

### 1.1 .NET 与 NuGet 镜像

- 工程目标 `net8.0` / `net8.0-windows`（WPF），需要 .NET 8 运行时；本机若只装了更高版本 SDK（如 10.x），仍可构建 net8.0 目标。
- **NuGet 源必须换国内镜像。** 在部分网络环境下 `nuget.org` 的 SSL 不通，还原会报 `NU1301`，且本机 NuGet 缓存通常为空 → 一个包都下不来、编译直接失败。

配置**用户级**（不动仓库、不影响他人）`~/.nuget/NuGet/NuGet.Config`：

```xml
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <packageSources>
    <clear />
    <add key="huaweicloud"
         value="https://repo.huaweicloud.com/repository/nuget/v3/index.json"
         protocolVersion="3" />
  </packageSources>
</configuration>
```

验证：`dotnet build WireCabinet.sln` 应 0 警告 0 错误。

### 1.2 本机覆盖配置（两处，**都不提交**）

| 文件 | 本机改法 | 作用 |
|------|----------|------|
| `src/WireCabinet.Hmi/appsettings.Local.json` | `Mes:ConnectionString` 置为**空字符串** | `MesOptions.IsConfigured = false` → `AppBootstrap` 选用 `SqliteMockMesGateway`，本机脱离内网即可跑通存料 / 归还 / 领用全流程 |
| `slot-config/io-modules.yaml` | `modules[].enabled` 全部置 `false` | `ModbusSlotHardwareService.IsConfigured = false` → `SlotControlService` 跳过真实开锁、直接写门态返回成功；同时不再每 2s 探测内网 IP（否则界面持续卡顿） |

说明：

- 配置加载顺序是 `appsettings.json` → `appsettings.Local.json`（后者覆盖前者），见 `src/WireCabinet.Hmi/App.xaml.cs`；所以**不要改共享的 `appsettings.json`**（现场机需要真连接串）。
- 硬件开关的判据是 `Modules.Any(m => m.Enabled && host 非空)`，见 `ModbusSlotHardwareService.cs`；`io-modules.yaml` 不存在时 `SlotIoConfig.Load()` 会回退读 `io-modules.template.yaml`。
- 这两个文件按 README 的设定本就是**本地/现场文件**（`io-modules.yaml` 由 `io-modules.template.yaml` 复制生成），**已从 git 索引移除并加入 `.gitignore`**。
- 到现场联调时把 `enabled` 改回 `true`、并在 Local 配置里填真实 MES 连接串。

### 1.3 运行

```bash
cd requirements/versions/0.1/wire-cabinet
dotnet build WireCabinet.sln
dotnet run --project src/WireCabinet.Hmi/WireCabinet.Hmi.csproj
```

首次启动会建库并补齐表结构。状态栏显示 `MES× | IO 0/4在线 | RCS○` 是**本机的正常表现**——读法见 §3.1。

## 2. 测试工程

- `src/WireCabinet.Tests`（xUnit / `net8.0`），随解决方案一起编译：`dotnet test WireCabinet.sln`
- **只引用非 WPF 层**（Core / Data / Flow / Slots / Slots.Hardware / Rcs）。`WireCabinet.Hmi` 是 `net8.0-windows`，测试工程无法引用
  → 挂在 Hmi 里的逻辑（`MhDoorOnlyService` / `AgvServices`）**暂不可自动化测试**；需要覆盖时先把判定逻辑下沉到 `Slots` / `Rcs`
- 现有测试：

| 测试类 | 覆盖 |
|--------|------|
| `OperationLogSchemaTests` | 全新库建表脚本含全部新列（防建表脚本与迁移清单分叉）；**老库补列后既有列与既有数据不变**，且幂等 |
| `OperationLogSinkTests` | 记录字段按列落库；**库写入失败时返回失败、不抛异常、转存待补偿**；告警事件触发 |
| `MesModeSelectionTests` | 本机配置确实把连接串覆盖为空 → 走 mock；共享配置仍保留现场连接串 |

## 3. 状态栏读法与已知坑

### 3.1 状态栏三项的真实含义

计算代码在 `src/WireCabinet.Hmi/MainWindow.xaml.cs` 的 `BuildInfraSummary`：

| 显示 | 含义 |
|------|------|
| `MES×` | **未配置真实 MES（走 mock）**，不是"连不上"。判据是连接串是否为空 |
| `IO 0/4在线` | 四个 IO 模块均不可达。本机不在厂区网时必然如此 |
| `RCS○` | 已配置但未连接（`✓`=已连接，`×`=未配置） |

> ⚠ `MES×` 用同一个符号表达了"未配置"和"连不上"两种完全不同的情况，本地开发/演示时容易被误判为故障。**不要靠状态栏判断 MES 模式。**

### 3.2 ⚠ mock MES 会「假成功」

`WireDiscoEqpSyncService.TryMarkInCabinet` / `TryClearFromCabinet` 判定成功**只看 `result.HasError`，从不检查 `RowsAffected`**（`WireDiscoEqpSyncService.cs`）。而 mock 的 SET 语句是 `UPDATE fw_material_indetail SET DISCOEQPNO = :disco_eqp_no WHERE sublot = :sublot`——在空的 mock 表上影响 0 行、不报错 → **被判定成功**。

后果：

1. **本机每启动一次应用，`RetryPendingBatch()` 就会把 `wire_mes_disco_sync` 里的待重试项标成 `success`**，而实际什么都没写。
2. 若 `data/app.db` 被提交或拷到现场，**现场会以为这些批号已同步到 MES**，真实的待处理项被掩盖——待重试队列本是现场发现"MES 没同步上"的唯一线索。

因此：

- **写操作的正确性不能用 mock 验证。**
- 做失败注入测试要用**会报错**的手段（例如 `DROP TABLE`），**不能用"目标行不存在"**，否则测试全绿但什么都没验证。
- 0.2 的记录写入已按此收紧：`SqliteOperationLogSink` 除 `HasError` 外还检查 `RowsAffected < 1` → 判失败。

### 3.3 其他

- 启动时会弹「中断快照」相关提示框的前提是 `mh_interrupted_load` / `op_interrupted_issue` 有数据；这两张表为空时不会弹。
- 首启会把 `OperationLogSchema` 的新列应用到既有 `app.db`（幂等 `ALTER TABLE ADD COLUMN`，只加列、不动既有列与数据）。

## 4. 已做的仓库清理（磁盘文件均保留）

| 文件 | 处理 | 原因 |
|------|------|------|
| `src/WireCabinet.Hmi/appsettings.Local.json` | 移出 git 跟踪 + 加入 `.gitignore` | 本地覆盖文件，每位开发者不同 |
| `slot-config/io-modules.yaml` | 同上 | 按 README 由 `io-modules.template.yaml` 复制生成；本机开发需改 `enabled` |
| `data/app.db` | 同上 | **运行时库**：跑一次程序就会改动它（含 §3.2 的假成功状态），跟踪它会让每次运行都产生 git 噪音，并有把假状态误提交的风险 |

> 三处均为 `git rm --cached`（**磁盘文件保留**，暂存区显示为删除）。**提交前请知会同事**：他拉取后这几个文件会从工作区消失——`io-modules.yaml` 可从 `io-modules.template.yaml` 复制回来，`app.db` 会在下次启动时按 `scripts/` 重建（重建得到 54 格 + 种子数据，手工录入的演示焊丝数据需重新录入）。
> 若要撤销：`git reset` 即恢复跟踪。

## 5. 开发起步顺序（建议）

第一批**只求跑通一条最小链路**，不要一次铺开全部动作：

1. 环境（§1）+ 测试工程（§2）——已完成
2. **已就绪的 0.2 代码前置**：
   - SQL catalog 条目 `app.operation_log.insert`（`requirements/data-access-sql/sql-catalog/items/`）
   - `OperationLogSchema` 列迁移（15 列 + 5 索引 + 待补偿表），已接入 `AppBootstrap` 启动流程
   - `IOperationLogSink` / `SqliteOperationLogSink`，已接入 `AppBootstrap.OperationLog`（组装根）
3. 把 sink **只挂到一个动作**上：MH 存料（链路最短、最好验证）
4. 断言：存料成功 → **恰好 1 条**记录、字段完整
5. **故障注入**断言 C1：注入会报错的 sink → 流程 outcome 不变、界面无「业务失败」
6. 跑 [../验收清单.md](../验收清单.md) §5 的五条脚本做回归（C2）→ 通过后再铺开其余动作
7. 最后做界面：页签、筛选、Excel 导出、批号追溯

理由：先把「写入 + 不阻断 + 回归」这条最小闭环打通。即使后面某个动作的挂接出问题，排障范围也始终是小的。
