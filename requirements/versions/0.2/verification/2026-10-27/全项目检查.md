# 2026-10-27 全项目检查

## 1. 范围与结论

产品基线：`2e1086c`（main，最近一次产品修复为 10-26 单实例守卫）。本轮检查覆盖运行时流程及 SQL、库存与 MES 同步、门态与控车门禁、记录/补偿/查询/导出、启动恢复、依赖和交付文档。

**本地复现 9 项问题：5 项 P1、4 项 P2；另验证 1 项数据库保护边界。** 本轮只做审查和隔离复现，没有修复产品行为。原有 284 项测试全部通过不能覆盖下述交叉场景。

- 本会话产品 Release 构建 0 警告 / 0 错误；测试 266 Core + 18 Windows HMI = 284，通过且无跳过。
- 用产品 `FlowLoader` / `SqlCatalog` 核对 6 个运行时流程、110 个节点、48 个 SQL 条目：缺失 SQL 引用 0、路由指向不存在节点 0、未知节点类型 0。此项只验证结构，不证明 Oracle SQL 和真实动作全部正确。
- 复现只用新建临时 SQLite 库、假 RCS 客户端；没有启动 WPF Application、没有调用硬件接口、没有连接现场、没有写 MES。
- 证据：[observed-results.json](observed-results.json)、[离线复现程序](audit-probe/Program.cs)、[依赖扫描原文](dependency-audit.json)。探针退出码 0 只表示完成观察，**不是产品验收通过**。

## 2. 本地复现的新问题

### A01 — P1：门态未知仍会自动清除中断领用库存

位置：`OpInterruptedIssueAutoComplete.cs:33`、`SlotDoorDisplay.cs:13`、`AppBootstrap.cs:175`。

自动收尾使用面向界面的 `IsDisplayOpen`。硬件已配置但没有 DI 快照或读取失败时，显示规则退回数据库 `door_state`；库里是 closed 就被当成可清库。它没有像正常 OP 关门确认那样，要求有效 DI 并重新读锁。

复现：临时库放一格 `available_wire / 领用待取 / closed`，标记早于 10 分钟；配置一个所有硬件方法均禁止调用的假硬件，不提供任何快照，直接运行产品 `TryRun()`。**实际完成 1 格，格口变 idle，批号变 NULL。** 另用 `ReadOk=false / LockClosed=null` 直接核对相同判据，结果也是允许。

影响：库里的历史门态不能证明实物已取走或门当前已关，通信故障时可能造成账物不符。建议清库要求明确、足够新的锁闭证据，未知态保留隔离；清库 SQL 还应按待处理状态和原批号做条件保护。

### A02 — P1：同秒待补偿记录仍会串格回填门时刻

位置：`OperationLogPendingStore.cs:165`、`OperationLogSink.cs:221`。

10-09 的 rowid 修复保护了已成功插入的正常路径；写入失败转待补偿后仍只靠 `(action_type, ts)` 找第一条未补关门时间的记录，没有格口或唯一动作标识。

复现：同一秒给 F-A01/F-A02 各写一条 `mh_take_wire`，用临时 INSERT 拒绝触发器让两条都入队；先关 F-A02（00:00:05），再关 F-A01（00:00:10），恢复后补写：

| 格口 | 实际关门 | 最终落库 |
|---|---|---|
| F-A01 | 00:00:10 | **00:00:05** |
| F-A02 | 00:00:05 | **00:00:10** |

两次回填都报成功。落库后事实保护触发器又禁止直接更正已填时间。建议给动作/队列提供稳定唯一关联，禁止按秒级时间猜测归属。

### A04 — P1：存取流程进行中，后台仍能自动派车回充

位置：`AgvServices.cs:558`、`LowBatteryChargeService.cs:96` / `GetDispatchBlockAsync`。

自动派车检查订单、车辆就绪和门全关，但没有检查 `WireSession.HasActiveSession` / 存取流程占用。门尚未打开时，正在输入/校验的业务流程也满足“门全关”。

复现：通过真实 `FlowCoordinator.TryBeginFlow` 开启 OP 流程，停在 `inputOperatorWorkInfo`；假车 IDLE、20% 电量、门全关，执行产品 `PollCycleAsync`。**流程与业务会话均仍 active，同时产生 1 个充电单。**

影响：作业尚未结束时车辆可能离站。建议存取与移动共享一套业务占用联锁，自动回充/返航与人工派车均须检查，并覆盖检查和下单之间的并发窗口。

### A05 — P1：RCS 刷新失败后，到站校验仍可能放行

位置：`MhStationAccess.cs:19`、`OpStationAccess.cs:19`、`HmiUiGateService.cs:33` / `:50`。

两种到站校验都在 `RefreshStatusAsync()` 后继续用旧状态判断，没有复查 `IsConnected`；UI 门控也不检查快照有效性。刷新失败虽然禁用了发车按钮，却没有使旧的“到站/停稳”失效。

复现：先连上假车，取得 OP 站 IDLE / AT_FINISHED；在到站校验内部刷新时注入断线。**IsConnected=false，但 MH 和 OP 流程到站校验都返回 Allowed=true，维护/MH 开门门控也没有阻断。** 这不同于“校验开始前已经断线”的路径，后者通常会因重连失败而拒绝。

影响：无法确认车辆是否仍停稳时，界面仍可能允许作业。建议刷新失败立即使作业门禁失效，并对状态设置有效期。

### A06 — P1：站点名称校验只保护了人工命令，自动路径可绕过

位置：`AgvServices.cs:324` / `:558`、`LowBatteryChargeService.cs:115` / `:163`。

复现：充电点配置名称在地图中不存在；人工 `GoChargeAsync` 明确拒绝，提示名称找不到；随后同一服务的后台轮询仍产生 **1 个充电单**。自动路径直接调用客户端，未使用人工路径的名称错误门禁。

另经代码核对：自动返航直接使用已记住的数字目标，未走人工发车/充电的“目的地不存在→名称重解析→重试”包装；此部分未另做完整地图换版复现。

影响：名称解析失败时仍可能使用旧数字号下自动订单；地图推送后的自动行为与人工行为不一致。建议所有下单入口复用同一套目标解析和有效性校验。

### A03 — P2：先补偿成功、后关门，会永久丢失记录关联

位置：`OperationLogSink.cs:221`、`:271`。

复现：业务记录写失败入队→故障恢复→后台补写成功→用户随后关门。原调用方的 rowid 仍为 NULL，只能去 active 队列找；队列已标 success，于是回填报“找不到它”。**最终记录门时刻空，待补偿 0。**

这是确定的先后顺序，**不需要并发竞态**。门长时间打开时，2 分钟后台重试可能先于关门。建议成功补写后保留 pending→最终记录 ID 映射，并让后到事件按同一唯一动作标识定位。

### A07 — P2：低电量自动回充下单没有存取记录留痕

位置：`LowBatteryChargeService.cs:96`。

复现：注入真实 SQLite 记录 sink，假车 IDLE、20% 电量，后台成功产生 1 个充电单；**app_operation_log 为 0 条、待补偿为 0 条**。当前方法成功和异常分支都没有调用 `_agvLog`。手动回充和自动返航的留痕不能替代这条自动回充记录。

建议补上成功与失败记录，连续同因失败沿用合并口径。

### A08 — P2：后台刷新会原地修改 UI 正在读取的格口列表

位置：`FlowSlotController.cs:19` / `:23`、`App.xaml.cs:110`。

`Slots` 暴露同一个 `List`，`Reload()` 先 Clear 再逐行 Add；硬件回调在后台执行 Reload，而多处 UI/流程直接枚举该集合。

复现受控交错：取得产品 `Slots` 枚举器并读一项→调用真实 Reload→继续枚举，抛 `Collection was modified; enumeration operation may not execute.`。**已证明该交错会抛异常，未在完整 HMI 并发压力下复现退出，也未据此归因历史崩溃。**

建议构造完整新快照后原子替换引用，或统一读写调度/同步，避免向外暴露正在变化的集合。

### A09 — P2：自动清库的说明存在库里，却在记录页和 Excel 中不可见

位置：`AppBootstrap.cs:191`、`OperationLogView.xaml.cs:344`、`OperationLogExcelExporter.cs:55`。

自动收尾把“程序中断、按门已关自动清库”的原因写进 `detail`；界面说明和导出第 16 列只读 `message` / `error_info`。

复现：读模型包含完整自动收尾 detail，真实导出后第 16 列仍只有“领用提交完成”。因此用户从界面/Excel 无法识别这是自动恢复后的结果。建议在现有说明投影中体现派生说明，保持事实列不可改写。

## 3. 另经代码确认的调度缺口

**C01 — P2：10 分钟宽限期到时未必会再尝试自动收尾。** 除启动外，`App.xaml.cs:107` 只在本轮 `closed.Count > 0` 时调用 `TryRun`。例如重启时中断领用刚过 5 分钟、门已关，启动扫描不会处理；后续全柜没有新关门事件，超过 10 分钟也不会再扫描，直到下次关门或重启。此项是调用点核对结论，没有伪装成已跑完整现场复现。应在轮询中按限频独立检查，先修 A01 的门态判定。

## 5. 安全依赖、数据保护与交付

### 5.1 依赖扫描

执行 `dotnet list WireCabinet.sln package --vulnerable --include-transitive --format json`，对 NuGet 当前公告核对，发现 **2 个传递依赖包、3 条公告**：

| 包 | 当前解析版本 | 扫描级别 | 公告 |
|---|---|---|---|
| SQLitePCLRaw.lib.e_sqlite3 | 2.1.6 | High | [CVE-2025-6965](https://github.com/advisories/GHSA-2m69-gcr7-jv3q) |
| System.Security.Cryptography.Pkcs | 8.0.0 | High / Moderate | [CVE-2026-84008](https://github.com/advisories/GHSA-846f-f764-76mx)、[CVE-2026-70162](https://github.com/advisories/GHSA-2fmv-rv2c-59x7) |

SQLite 公告涉及构造 SQL 触发的内存损坏；当前应用使用 catalog/参数化访问，本轮没有证明用户输入能到达该利用条件。Pkcs 公告涉及处理攻击者构造的 CMS/X.509 数据导致 CPU 耗尽；应用源码未找到直接调用 SignedCms/EnvelopedCms，Oracle 依赖内部可达性未分析。**包版本命中不等于已经证实现场可被远程攻击。**

建议安排依赖修补与兼容性回归：Pkcs 8.0 分支公告修复版为 8.0.2；SQLite 需选择实际携带修复原生 SQLite 的受支持 provider/bundle 并验证 `sqlite_version()`，不能只盲升一个仍被标记的 2.1.x 包。本轮未修改包版本或现场运行时。

### 5.2 数据库保护边界 B01

临时库实测：事实 UPDATE 有触发器保护，但直接 `DELETE FROM app_operation_log` 能删除 1 行。源码没有发现产品业务主动 DELETE；现有保障是“应用路径禁止删除 + 库层限制 UPDATE”，**不是数据库层连 DELETE 也拒绝**。若需要库层防误删，应另补删除触发器及独立验收；对具有完整文件权限的人，触发器本身也不等于防篡改存储。

### 5.3 工程与交付现状

- 本地 main 相对当前本地记录的 `mirror/main` 领先 67 个提交；未 fetch，未把它推断成远端实时状态。
- 两个既有配置修改（`.build-check/appsettings.json`、SDK Sample 配置）仍保留，不能混入审查提交/交付包；本轮未读取或输出其中凭据值。
- 本仓库未见 `.github` 自动构建/测试流水线，未见 SDK `global.json` 或 NuGet 锁文件。人工检查可通过，但重复构建和交付一致性仍依赖操作规程。
- 部署仍须配套 DLL、catalog、运行时 flows、站点配置，且保留现场 Local、IO 配置和数据库。只覆盖 DLL 不足以证明行为正确，exe 时间戳也不代表全部程序集版本。
- 产品与 lab 两套 FlowEngine 仍有维护分叉；运行时流程/SQL依赖仓库目录结构，交付包应有配套 manifest/hash 和启动自检，避免缺条目后静默降级。
- catalog 的 index 漏登记 `app.operation_log.mark_auto_pickup`、`app.slot.mark_issue_state`、`app.slot.list_issue_pending`；运行时扫描 items 目录因此仍能加载，但目录索引与交付检查不能视为完整。
- “应用库业务 SQL 全进 catalog”的约定未全面落实：`SlotControlService` / `FlowSlotController` 仍内联多处 app_slot 查询与状态更新。迁移 DDL 和补偿基础设施 SQL应另论，业务 SQL 的两套定义仍需收拢。
