## 2. 新增

### 2.1 功能

- 任一存取动作（存料 / 归还 / 领用 / 取出 / 开门 / 试开 / 控车回充 / 失败 / 无指令开门 / 开门即清空）**自动写入一条记录**，一次业务操作一条。
- 「存取记录」页签：六项条件组合查询、时间倒序、每页 20 条。
- **按批号追溯全程**：入库 → 在柜 → 归还 → 被取走。
- **导出 Excel**（本地目录 / U 盘）。
- **写入失败补偿**：不阻断业务 + 状态栏告警 + 后台自动重试 + 待补偿列表人工重试。

详见 [需求范围 §3](需求范围.md)。

### 2.2 应用库

- `app_operation_log`：0.1 已建表、全工程零代码引用，故**只扩列**，既有列与既有数据不动。
- 新增 15 列（§5.2）与 5 个查询索引（`ts` / `lot_no` / `slot_no` / `operator_id` / `eqp_no`）。
- 新增表 `operation_log_pending`：写入失败时整条记录以 JSON 转存，供后台与人工重试。
- 记录表**只增不删**：有测试扫描全部 catalog 与源码，禁止出现
  `UPDATE` / `DELETE FROM app_operation_log`（验收 §6「DB 层无 UPDATE / DELETE 记录表」）。

### 2.3 SQL catalog

在 `requirements/data-access-sql/sql-catalog/items/` 新增（已同步 `index.yaml`）：

| sql_id | 用途 | 操作 |
|---|---|---|
| `app.operation_log.insert` | 写入记录 | write |
| `app.operation_log.list_by_filter` | 六项条件组合查询（分页、时间倒序） | read |
| `app.operation_log.list_for_export` | 导出取数（同条件、不分页） | read |
| `app.operation_log.timeline_by_lot` | 按批号取全程时间线（正序、不分页） | read |

动态条件不拼 SQL：用 `:x IS NULL OR col = :x` 的参数守卫，与既有 `app.slot.list_by_filter` 同法。

计划稿里列的 `app.operation_log.mark_access` **未做**为独立条目 —— 查看与导出的留痕直接复用
`app.operation_log.insert`（动作类型区分），少一个条目少一处不一致。

### 2.4 动作类型（`app_operation_log.action_type`）

| 值 | 含义 | 对应验收矩阵 |
|---|---|---|
| `mh_load_available_wire` | MH 存入可用焊丝 | 第 1 项 |
| `op_return_wire` | OP 归还旧焊丝 | 第 2 项 |
| `op_issue_available_wire` | OP 领用新焊丝 | 第 3 项 |
| `op_take_wire` | OP 取出焊丝（含门开 / 关门时刻） | 第 4 项 |
| `mh_open_slot` | MH 打开单个格口（无指令开门也复用此类型，带 `is_uncommanded = 1`） | 第 5、10 项 |
| `mh_open_slots_batch` | MH 批量打开格口（**每个被打开的格口各一条**） | 第 6 项 |
| `maint_trial_open` | 维护人员试开 | 第 7 项 |
| `agv_move` | AGV 控车（下单 / 暂停 / 继续 / 取消 / 返航，具体动作写在 `message`） | 第 8 项 |
| `agv_charge` | AGV 自动回充 | 第 8 项 |
| `mh_assume_empty` | 开门即清空（`is_cleared = 1`） | 第 11 项 |
| `view_operation_log` | 查看记录页（留痕） | §3.7 |
| `export_operation_log` | 导出记录（留痕） | §3.5、§3.7 |

失败**不单独成动作类型**：同一动作记一条，`result = 失败` + `error_info` 写原因（§3.1 设计说明 1）。
无指令开门亦**不新增类型**，按 §3.1 设计说明 3 并入开门记录、以 `is_uncommanded` 表达。

### 2.5 界面

- `src/WireCabinet.Hmi/MainWindow.xaml`：顶栏新增第 6 个页签，标签用 **4 字「存取记录」**。
- 新增 `Views/OperationLogView.xaml(.cs)`：六项筛选 + 列表 + 追溯 + 导出 + 待补偿列表（同区域切换）。
- 门禁 `Services/OperationLogAccessGate.cs`：物料员**或**维护密码均可进入，操作员无入口（§2）。

**顶栏空间已实测并按实测调整**：加第 6 个页签时 6 个页签按原尺寸共需约 890px，
而顶栏只留得出约 736px（标题 + 窗口按钮），会压到标题且标签被截断。
处理：`Styles/IndustrialTheme.xaml` 的 `RoleTabButton` 横向内边距 28→12、字号 17→16，
纵向内边距 10→12 补回触控高度（约 45px，不低于约束的 44px）。已在 1024×768 实机截图核对。

### 2.6 写入挂接点（实际落地位置）

| 动作 | 挂接位置 |
|---|---|
| 存料 | `FlowEngine`：`app.slot.bind_wire` 成功后 |
| 归还 / 领用 | `FlowEngine`：`submitWireReturn` / `submitWireIssue` 节点（两节点共用同一 sql_id，故按**节点 id** 区分） |
| 取出 | `FlowEngine`：`app.slot.complete_issue_pickup`（关门后，单独成条） |
| MH 开单格 / 批量 / 维护试开 / 无指令开门 / 开门即清空 | `WireCabinet.Slots/SlotDoorActionLog.cs`（由 `MhDoorOnlyService` 与门态巡检调用） |
| 控车 / 回充 / 返航 | `WireCabinet.Rcs/AgvActionLog.cs`（由 `AgvServices`、`LowBatteryChargeService` 调用） |
| 查看 / 导出留痕 | `OperationLogView` |

记录器刻意放在 `Slots` / `Rcs` 而非界面层：界面是 net8.0-windows，测试工程引用不了，
而这里最容易错的是「批量开门条数」与「不按轮询 tick 记录」这类必须靠测试钉住的性质。

## 3. 对 0.1 既有行为的修正（**与计划稿的差异**）

计划稿写的是「0.2 不改动 0.1 的任何既有行为」。实际实施中，为了把记录功能做对，
发现并修正了 0.1 的 4 处既有缺陷。**这几处与记录功能本身无关，回滚记录功能不会撤销它们**（见 §7）：

| # | 位置 | 0.1 的问题 | 修正 |
|---|---|---|---|
| 1 | `WireCabinet.Data/Mes/WireDiscoEqpSyncService.cs` | `TryMarkInCabinet` / `TryClearFromCabinet` / `ManualSet` / `ManualClear` 只看 `HasError` 判成功。UPDATE 影响 0 行时 Oracle 与 SQLite 都不报错，于是**报成功并把待补偿状态标成已同步**，`ManualSet` 还会给审计流水落一条谎报「改过 MES」的记录 | 四处改用 `HasError \|\| RowsAffected < 1`；另修 `IsAlreadyClearInMes` 把「读取失败」当成「已是 NULL」而短路报成功 |
| 2 | `requirements/validation/wire-flow-lab/.../operator_return_wire_and_issue_available_wire/flow.yaml`（+ `flow.generated.yaml`） | 结尾 `success: End`，而 `End` 不是已定义节点，且该流程**没有 success 终止节点**。操作员成功走完存废取新后，界面显示的是「路由指向不存在的节点 'End'」 | 补 `endSuccess` 终止节点并把 `success` 指过去。**这是唯一一处修改 0.1 流程定义**，按 lab README 的约定（发现的问题回写到 flow-sql-map）执行 |
| 3 | `WireCabinet.Flow/Flows/FlowEngine.cs` | sql_id 解析只做了 mock→正式（Oracle 模式）单向，且 query/decision 走模式感知解析、write/slot 节点直接 `Catalog.Find` 绕过模式选择。结果操作员流程在 mock 模式下执行 Oracle SQL（`no such function: NVL`），`submitWireReturn` 把 PL/SQL `DECLARE` 块当普通 SQL 执行 | 收敛到 `SqlCatalog.FindForMode`：双向解析 + 各节点类型统一 |
| 4 | `SqliteDb.Initialize` / `AppBootstrap`（MES mock 环境） | mock MES 表（`mv_fw_username` / `fw_eqpres_eqpinformation` / `fw_wip_trans` / `v_fw_wip_sublot`）产品脚本从不创建，操作员流程在本机完全跑不起来 | 新增 `WireMesMockSchema.Ensure`，作为**每次启动**执行的幂等迁移（建库脚本只在首次建库时执行，老库拿不到） |

> 第 2～4 处都是本机/验证环境相关（流程定义与 mock 环境），第 1 处**影响现场 Oracle 行为**，
> 建议单独告知需求方：它修正的是「MES 同步谎报成功」这个既有缺陷。

## 5. 数据库升级

### 5.1 问题

`scripts/schema.sqlite.sql` 全部使用 `CREATE TABLE IF NOT EXISTS`，而 `SqliteDb.Initialize` 只是顺序执行建表与种子脚本、**没有列级迁移**（且只在**首次建库**时执行）。
因此：**现场已存在的 `data/app.db` 不会因新脚本而获得新列**，只改建表语句会让代码访问新列时报 `no such column`。

### 5.2 `app_operation_log` 新增列（15）

| 列 | 类型 | 说明 |
|---|---|---|
| `operator_name` | TEXT | 操作人姓名 |
| `operator_team` | TEXT | 班组 |
| `operator_role` | TEXT | MH / OP / MAINT |
| `action_type` | TEXT | 动作类型（§2.4） |
| `wire_spec` | TEXT | 焊丝规格 |
| `eqp_no` | TEXT | 机台号 |
| `product_lot_no` | TEXT | 产品批次号 / 领用工单批次号 |
| `qty` | REAL | 数量 |
| `remain_qty` | REAL | 剩余数量 |
| `station` | TEXT | 作业站点 |
| `result` | TEXT | 成功 / 失败 |
| `door_open_ts` | TEXT | 格口开门时间 |
| `door_close_ts` | TEXT | 格口关门时间（§3.3 定义为「关门确认时刻」） |
| `is_cleared` | INTEGER DEFAULT 0 | 「开门即清空」标记 |
| `is_uncommanded` | INTEGER DEFAULT 0 | 「无指令开门」标记 |

### 5.3 `operation_log_pending` 新增列（2）

| 列 | 类型 | 说明 |
|---|---|---|
| `status` | TEXT DEFAULT 'pending' | `pending` / `failed` / `success` |
| `next_retry_at` | TEXT | 下次自动重试时刻（UTC，往返格式） |

### 5.4 迁移方案（已实现）

`WireCabinet.Data/Data/OperationLogSchema.cs`：先 `PRAGMA table_info` 判断、再 `ALTER TABLE ADD COLUMN`，
幂等可重复执行，在应用启动时先于任何记录写入运行；`scripts/schema.sqlite.sql` 同步补上新列，
保证全新库一次建对。**只加列**，不修改、不删除既有列，也不改动既有数据。

### 5.5 并发写入（**未做，现场需关注**）

记录写入与既有写入者共用同一个 SQLite 文件：硬件轮询约 2s、AGV 轮询 5s、MES 对账重试 2min。
当前连接串只有 `DataSource`，**未开 WAL、未显式设 `busy_timeout`**。并发写不会立刻报错，
但可能阻塞到默认超时，表现为**界面卡顿**而非异常——这类问题最难排查。

计划稿建议的 WAL + `busy_timeout` 本次**没有实施**。若现场出现卡顿，优先从这里查，
并重点关注验收 §9 的 C4（批量开格口耗时对比）。

## 7. 回滚方式

- **记录功能回滚**：停用页签入口 + 停止写入挂接即可（`IOperationLogSink` 换成 `NullOperationLogSink` 则写入与补偿一并停止）。
- **数据库回滚**：新增的 17 列**无需删除**。0.1 全工程不引用 `app_operation_log`，多出的列不影响既有查询与写入。
- 记录表**只增不改**，回滚不产生数据不一致。
- ⚠ **§3 的 4 处 0.1 修正不随记录功能回滚**——它们与记录功能无关，回滚应单独评估（尤其第 1 处影响 Oracle 现场行为）。

## 8. 已知限制（交付时随程序提供）

| 限制 | 说明 |
|---|---|
| 查看 / 导出的留痕没有操作人 | §2 的门禁按需求「复用既有密码门禁」，只有密码没有工号，故留痕只能记角色（`MH` / `MAINT`）。MH 界面的开门/存料记录有工号（该界面新增了操作人输入） |
| 归档与备份策略未落地 | 验收 §6 与交付物清单要求的归档周期、备份方案**尚未写入运维说明**，待补 |
| 无硬件/内网时无法验收 | 验收 §1 明确「全部真实联调，不提供 Mock」，§10 把「依赖 Mock 完成验收」列为未通过条件。维护试开、无指令开门、开门即清空、控车六命令的正向路径、C2、C4 均需现场设备 |
| MES 真库路径未验证 | 全部实现与验证基于 SQLite mock。真库的 Oracle 专属写法（`NVL`、`FUN_MAT_TRANS_NEW` 等 PL/SQL 存储函数）从未执行过，现场可能需修改若干 SQL 条目 |
