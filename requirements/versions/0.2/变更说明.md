## 2. 新增

### 2.1 功能

- 任一存取业务动作自动写入一条记录；格口开门和关门分别追加事件，不回写既有记录。
- 「存取记录」页签：六项条件组合查询、时间倒序、每页 20 条。
- **按批号追溯全程**：入库 → 在柜 → 归还 → 被取走。
- **导出 Excel**（本地目录 / U 盘）。
- **写入失败补偿**：不阻断业务 + 状态栏告警 + 后台自动重试 + 待补偿列表人工重试。

详见 [需求范围 §3](需求范围.md)。

### 2.2 应用库

- `app_operation_log`：0.1 已建表、全工程零代码引用，故**只扩列**，既有列与既有数据不动。
- 新增 15 列（§5.2）与 5 个查询索引（`ts` / `lot_no` / `slot_no` / `operator_id` / `eqp_no`）。
- 新增表 `operation_log_pending`：写入失败时整条记录以 JSON 转存，供后台与人工重试。
- 记录表**只增不删**：有测试扫描全部 catalog 与源码，禁止出现
  `UPDATE` / `DELETE FROM app_operation_log`（验收 §6「DB 层无 UPDATE / DELETE 记录表」）。

### 2.3 SQL catalog

在 `requirements/data-access-sql/sql-catalog/items/` 新增（已同步 `index.yaml`）：

| sql_id | 用途 | 操作 |
|---|---|---|
| `app.operation_log.insert` | 写入记录 | write |
| `app.operation_log.list_by_filter` | 六项条件组合查询（分页、时间倒序） | read |

### 2.7 记录口径优化（2026-10-09，**验收标准随之变更**）

现场做完一整轮 MH 存料 + OP 存废取新后量出：当天 481 条记录里 **84% 是过程/推导记录**，
平均 1 次人的动作写出约 12 条，记录页可读性差。改为**「一次人的操作 / 有业务意义的动作 = 一条记录，
开门、关门、清空是这条上的字段」**（`需求范围.md` §3.2 本来就有这条原则，本次是回归它并删掉例外）。
草案、量化数据、改前改后例子见 [记录口径优化](记录口径优化-20261009.md)。

| 场景 | 改前 | 改后 |
|---|---|---|
| 存一盘焊丝 | 3 条（开门 + 关门 + 存料） | **1 条**（门时刻挂字段） |
| 一次批量开门（53 格） | 159 条 | **53 条**（逐格一条「MH 取出旧焊丝」） |
| OP 一轮存废取新 | 7 条 | **2 条**（归还 / 领用并取出） |
| 自动返航连续失败 9 次 | 9 条 | **1 条**（`detail.count` / `first_ts` / `last_ts`） |

落地要点：

1. **门事件并入业务记录**：存料的 `updateDB` 在关门之后，直接带上门时刻（**2026-10-10 现场修正**：门往往由人工/硬件**先**关掉，流程推进到关门节点时 `app_slot.door_state` 已是 `closed`、`CloseNextOpenDoor()` 返回 null，必须改成「本流程开过门就补上时刻」，否则这 1 条会只有开门时刻）；归还 / 领用是**先提交、后开关门**的，
   提交时先落库（门时刻 NULL），关门确认后用 `app.operation_log.backfill_door_ts` 只补空字段回填。
2. **领用与取出合并成一条**（决议 1 于 2026-10-09 变更；`验收清单.md` 原先把「合并」列为未通过条件，已删）。
3. **批量开门逐格一条**（按需求方 2026-10-09 确认：一次批量在语义上就是「逐格取走」，而「取出一个一定记一条」）；「开门即清空」降级为开门记录上的 `is_cleared` 与批号。
4. **自动路径连续失败合并**（`AgvActionLog.RecordAutoFailure`）。
5. 新增 2 列：`detail`（JSON，只用于自动路径重复失败统计）、`corrects_id`；新增 2 个 catalog 写条目（回填门时刻、更新失败 detail）。
6. 最终按逐格记录显示格口号与被清批号；导出为下述 16 列，不再输出「格口数」「明细」。

**同日再收敛（需求方 2026-10-09 复核后确认）**：这个功能是「存取记录」，所以
- **动作类型收敛为 2×2**：MH 存入焊丝 / MH 取出旧焊丝、OP 归还旧焊丝 / OP 领用新焊丝，
  另加维护试开与无指令开门（`uncommanded_open`，独立类型，不再复用开门类型）。
  规则只有一条：**取出一个一定记一条，存放一个一定记一条**。
  旧动作码 `mh_open_slot`/`mh_open_slots_batch`/`mh_assume_empty`/`door_open` 不再新写、也不进筛选下拉，但仍显示历史中文名；
  `op_take_wire` 仍用于取出后库存更新失败，`door_close` 仍用于无指令开门的配对关门。
- **批量开门改回逐格**（原草案建议「1 条 + 格口清单」，已按需求方意见推翻）。
- **导出列收敛为 16 列**：时间 / 动作 / 操作人 / 角色 / 格口 / 焊丝批号 / 焊丝规格 / 数量 /
  剩余数量 / 机台号 / 工单号 / 门开时间 / 门关时间 / 结果 / 失败原因 / 说明。
  删掉：作业站点（条款一并删除）、格口数 / 明细、MES 调用结果 / 格口开锁结果、开门即清空 / 无指令开门
  （已由动作类型表达）、流程 / 节点（排障用，留库）；操作人工号并入「操作人」。
  **`说明 message` 是这轮补进来的** —— 之前两版导出都漏了它，而它是唯一写「到底发生了什么」的那列。
- `FlowEngine` 里那套「按流程抑制门事件」的逻辑随之删除：产品只跑两个业务流程，
  这条路径本就不可达。

**未做**：更正记录 UI（`corrects_id` 与「默认只看最新有效版本」的查询投影已就位，但没有写更正记录的入口）；
历史 9624 条老记录原样保留，展示层未做聚合折叠。

## 3. 对 0.1 既有行为的修正（**与计划稿的差异**）

计划稿写的是「0.2 不改动 0.1 的任何既有行为」。实际实施中，为了把记录功能做对，
发现并修正了 0.1 的 4 处既有缺陷。**这几处与记录功能本身无关，回滚记录功能不会撤销它们**（见 §7）：

| # | 位置 | 0.1 的问题 | 修正 |
|---|---|---|---|
| 1 | `WireCabinet.Data/Mes/WireDiscoEqpSyncService.cs` | `TryMarkInCabinet` / `TryClearFromCabinet` / `ManualSet` / `ManualClear` 只看 `HasError` 判成功。UPDATE 影响 0 行时 Oracle 与 SQLite 都不报错，于是**报成功并把待补偿状态标成已同步**，`ManualSet` 还会给审计流水落一条谎报「改过 MES」的记录 | 四处改用 `HasError \|\| RowsAffected < 1`；另修 `IsAlreadyClearInMes` 把「读取失败」当成「已是 NULL」而短路报成功 |
| 2 | `requirements/validation/wire-flow-lab/.../operator_return_wire_and_issue_available_wire/flow.yaml`（+ `flow.generated.yaml`） | 结尾 `success: End`，而 `End` 不是已定义节点，且该流程**没有 success 终止节点**。操作员成功走完存废取新后，界面显示的是「路由指向不存在的节点 'End'」 | 补 `endSuccess` 终止节点并把 `success` 指过去。**这是唯一一处修改 0.1 流程定义**，按 lab README 的约定（发现的问题回写到 flow-sql-map）执行 |
| 3 | `WireCabinet.Flow/Flows/FlowEngine.cs` | sql_id 解析只做了 mock→正式（Oracle 模式）单向，且 query/decision 走模式感知解析、write/slot 节点直接 `Catalog.Find` 绕过模式选择。结果操作员流程在 mock 模式下执行 Oracle SQL（`no such function: NVL`），`submitWireReturn` 把 PL/SQL `DECLARE` 块当普通 SQL 执行 | 收敛到 `SqlCatalog.FindForMode`：双向解析 + 各节点类型统一 |
| 4 | `SqliteDb.Initialize` / `AppBootstrap`（MES mock 环境） | mock MES 表（`mv_fw_username` / `fw_eqpres_eqpinformation` / `fw_wip_trans` / `v_fw_wip_sublot`）产品脚本从不创建，操作员流程在本机完全跑不起来 | 新增 `WireMesMockSchema.Ensure`，作为**每次启动**执行的幂等迁移（建库脚本只在首次建库时执行，老库拿不到） |

> 第 2～4 处都是本机/验证环境相关（流程定义与 mock 环境），第 1 处**影响现场 Oracle 行为**，
> 建议单独告知需求方：它修正的是「MES 同步谎报成功」这个既有缺陷。

## 5. 数据库升级

### 5.1 问题

`scripts/schema.sqlite.sql` 全部使用 `CREATE TABLE IF NOT EXISTS`，而 `SqliteDb.Initialize` 只是顺序执行建表与种子脚本、**没有列级迁移**（且只在**首次建库**时执行）。
因此：**现场已存在的 `data/app.db` 不会因新脚本而获得新列**，只改建表语句会让代码访问新列时报 `no such column`。

### 5.2 `app_operation_log` 新增列（18）

| 列 | 类型 | 说明 |
|---|---|---|
| `operator_name` | TEXT | 操作人姓名 |
| `operator_team` | TEXT | 班组 |
| `operator_role` | TEXT | MH / OP / MAINT |
| `action_type` | TEXT | 动作类型（§2.4） |
| `wire_spec` | TEXT | 焊丝规格 |
| `eqp_no` | TEXT | 机台号 |
| `product_lot_no` | TEXT | 产品批次号 / 领用工单批次号 |
| `qty` | REAL | 数量 |
| `remain_qty` | REAL | 剩余数量 |
| `result` | TEXT | 成功 / 失败 |
| `door_open_ts` | TEXT | 格口开门时间 |
| `door_close_ts` | TEXT | 格口关门时间（§3.3 定义为「关门确认时刻」） |
| `is_cleared` | INTEGER DEFAULT 0 | 「开门即清空」标记 |
| `is_uncommanded` | INTEGER DEFAULT 0 | 「无指令开门」标记 |

### 5.3 `operation_log_pending` 新增列（2）

| 列 | 类型 | 说明 |
|---|---|---|

### 5.4 迁移方案（已实现）

`WireCabinet.Data/Data/OperationLogSchema.cs`：先 `PRAGMA table_info` 判断、再 `ALTER TABLE ADD COLUMN`，
幂等可重复执行，在应用启动时先于任何记录写入运行；`scripts/schema.sqlite.sql` 同步补上新列，
保证全新库一次建对。**只加列**，不修改、不删除既有列，也不改动既有数据。

### 5.5 并发写入（**已实施**）

背景：记录写入与既有写入者共用同一个 SQLite 文件——硬件轮询约 2s、AGV 轮询 5s、
MES 对账重试 2min。默认的 rollback journal 模式下读写互斥，争用**不会报错**，
只表现为**界面卡顿**，是现场最难排查的那类问题。

已做两项（均只改连接初始化，不动任何业务逻辑）：

| 措施 | 做法 |
|---|---|
| 忙等待上限 | 连接串设 `DefaultTimeout = 15s`（`SqliteDb.BusyTimeoutSeconds`） |
| 开启 WAL | `SqliteDb.EnsureWal()`，在**每次启动的迁移链**里执行 `PRAGMA journal_mode=WAL` |

WAL 之所以放在启动迁移链而不是建库脚本里：它是**库文件的持久属性**，而建库脚本只在
首次建库时执行——现场已存在的 `app.db` 只能靠每次启动这条路径补上。已实测确认现场库为 wal。

> 注意：WAL 会在库目录多出 `app.db-wal` / `app.db-shm` 两个附属文件（**正常现象**，已加入
> `.gitignore`）。备份与拷贝的注意事项见 [运维说明-归档与备份.md](运维说明-归档与备份.md)。

**未做**：计划稿里「记录写入采用排队 + 单写通道」这一条没做——当前是写入方直接调用。
若现场仍出现卡顿，从这里着手；并关注验收 §9 的 C4（批量开格口耗时对比）。

### 5.6 时间列的口径（**存 UTC、看本地**）

`ts` / `door_open_ts` / `door_close_ts` 在库里**存 UTC**（补偿写入仍保留原动作时间），
而界面显示与筛选条件按**本地时区**。两个方向都要转，换算集中在
`WireCabinet.Data/Data/OperationLogTime.cs`（时区可注入，便于测试与多机一致）。

**只转显示、不转筛选会留下更难发现的错**：按墙上钟 17:00–18:00 查询会一条都查不到
（库里那条是 09:19），而这种错不报错、只表现为「查不到」，最容易被当成「没有记录」。
已有用例覆盖两个方向与跨日边界。

排查提示：直接查库看到的 `ts` 会比墙上钟**慢 8 小时**，那是正常的；界面与导出看到的是本地时间。

### 5.7 「只增不删」收窄为「业务事实不可改写」（**已实施**，2026-10-09）

原约束是「`app_operation_log` 不得出现任何 `UPDATE` / `DELETE`」，由
`OperationLogRetentionTests` 扫全部 catalog 与源码强制。它挡住了「后到的信息填不进去」——
归还 / 领用的关门时刻在写记录时还不存在，只能再写一条配对记录，**约束自己在制造冗余**。

现收窄为「**业务事实不可改写**」，只放行两种写法（正则白名单 + 库层触发器双保险）：

| 放行 | 说明 |
|---|---|
| 补齐 NULL 门时刻 | `app.operation_log.backfill_door_ts`：`SET door_open_ts/door_close_ts … WHERE id = :id AND door_close_ts IS NULL`（**按主键定位**，不是按 ts —— ts 只到秒、批量开门每格 400ms，同秒两条会把两条都填成同一个关门时刻；而且 UPDATE 先执行、后检查影响行数，检查拦不住已经写坏的行） |
| 更新失败记录 `detail` | `app.operation_log.update_detail`：过程派生字段（重复失败统计），`WHERE … result = '失败'` |

库层另有 `trg_app_operation_log_append_only`（`BEFORE UPDATE` 触发器）：除上述两类之外的任何列改动一律 `RAISE(ABORT)`。

**回填的补偿路径**：写入记录时把 rowid 一起带回来（`OperationLogWriteResult.RowId`），关门回填按它定位。
若那条记录没落库（写入失败、转了待补偿，拿不到 rowid），就把门时刻补进队列里那条 `entry_json`
（改的是待补偿表，不是记录表，所以不受上面的白名单约束），重试落库时记录就是完整的。
**补丁更新失败必须报失败** —— 早先这里丢掉了执行结果，UPDATE 失败也报成功，门时刻实际没保存却当成补好了。
真补不上会写进流程 findings，界面上看得见。部署前复查另发现「回填 SQL 本身报错时没有持久补偿任务」，
见 [部署前复查](verification/2026-10-09/部署前复查.md)（该项尚未修）。
`DELETE` 仍然完全禁止。更正错误记录的正路是「另加一条更正记录」（`corrects_id` 列已就位），不是原地改。

## 7. 回滚方式

- **记录功能回滚**：停用页签入口 + 停止写入挂接即可（`IOperationLogSink` 换成 `NullOperationLogSink` 则写入与补偿一并停止）。

- 记录表**只增不改**，回滚不产生数据不一致。
- ⚠ **§3 的 4 处 0.1 修正不随记录功能回滚**——它们与记录功能无关，回滚应单独评估（尤其第 1 处影响 Oracle 现场行为）。
