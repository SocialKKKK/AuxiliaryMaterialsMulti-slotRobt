## 0. 通用准备（每轮都做）

1. 连隧道：`cd /d/code/_agv-probe && ./connect.sh` → `ssh agv-cabinet`。
2. **取基线**：动作前拉一次库副本（**db + wal + shm 三件套**），记下 `ts_max_utc`：

   ```bash
   scp -O -i keys/site_key -P 122 ht@127.0.0.1:C:/Users/HT/Desktop/AuxiliaryMaterialsMulti-slotRobt/requirements/versions/0.1/wire-cabinet/data/app.db{,-wal,-shm} /tmp/db/
   python requirements/versions/0.2/autotest/dbcheck.py snapshot /tmp/db/app.db
   ```

3. 动作做完后，**只按时间窗核对**（不带 `--since` 会被历史数据误伤）：

   ```bash
   python dbcheck.py counts /tmp/db/app.db --since "<本轮开始 UTC>"
   python dbcheck.py pairs  /tmp/db/app.db --since "<本轮开始 UTC>"
   ```

4. 判定口径：**一次「人的操作」= 恰好 1 条**（一轮存废取新 = 2 条）；开门/关门/清空是这条上的字段，不再单独成条。

| 1 | MH 存 1 盘焊丝（批号 → MES 校验 → 分配空格口 → 开锁 → 放入 → 关门） | 产生 **1 条**「MH 存入焊丝」，含规格/批号/格位/时间 + 该格 `door_open_ts`/`door_close_ts` | ☐ 界面演示 |

| 4 | 继续走 OP 归还 / 领用 / 取出，再按同批号追溯 | 可见 **入库 → 在柜 → 归还 → 被取走** 完整链路 | ☐ |

## 脚本 5：写入失败不阻断业务并可补偿

| 步 | 操作 | 期望 | 状态 |
|---|---|---|---|
| 1 | 临时改名 `app_operation_log`（保留待补偿表可写） | — | ☐ 需放行改库 |
| 2 | 做一次存料 | **业务照常完成**；状态栏出现写入失败告警；待补偿列表出现 **1 条** | ☐ |
| 3 | 改回表名 → 点「全部重试」 | 补写成功；记录时间仍为原动作时刻；条数与待补偿项一致 | ☐ |
| 4 | 制造一次业务失败（如不存在的批号） | `result=失败` 且 `error_info` 有原因 | ✅ 已验（MES ORA-20007 共 4 条） |
| 5 | 补偿并发不重复：人工点重试的同时后台也跑 | 记录表只多 1 条 | ☐ |

> 脚本 5 的失败注入手段需现场约定：**临时改名 `app_operation_log`**，改回后必须确认 HMI 恢复正常写入。
