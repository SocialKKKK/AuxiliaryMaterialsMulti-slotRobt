## 2. 按风险排序的验证步骤

### ⚠ 第 1 步：MES 真库能不能通

最高风险项：**所有实现与验证都基于 SQLite mock，Oracle 真库的 SQL 从未执行过。**

- [ ] 应用启动后底部状态栏显示 `MES✓`（不是 `MES×`）
- [ ] 走一次「MH 存入可用焊丝」：批号能查到规格、能分配格口
- [ ] 走一次「操作员存废取新」：工号能查到姓名、机台能查到产品批号

**若这一步报错**，多半是 MES 侧 SQL 的方言或数据形状问题。已做的预检：流程引用的每个 `sql_id` 在 Oracle 模式下都能解析到正式条目、11 个 mock 条目都有正式镜像（不会因缺条目断链）。所以问题会出在 SQL 内容，看流程 Trace 或日志里的 `RenderedSql` 与报错原文，改 `requirements/data-access-sql/sql-catalog/items/` 里对应条目。

### 第 2 步：记录写入（一眼可辨）

- [ ] 存料成功后打开「存取记录」页签：应有 1 条「MH 存入可用焊丝」，含**规格、批号、格位、时间**
- [ ] **时间与墙上钟一致**（这条修过：库里存 UTC、界面显示本地；若显示慢 8 小时说明拿的是旧构建）
- [ ] 操作人列有「姓名(工号)」——**前提是 MH 界面的操作人工号框填了工号**（不填则该列为空，属预期）
- [ ] 走一次操作员存废取新：应产生**恰好 3 条**（归还 / 领用 / 取出），且取出那条含**门开与关门时刻**

### 第 3 步：查询 / 追溯 / 导出

- [ ] 六项筛选逐个单独用一遍，再组合一次（如 时间范围 + 格口 + 动作类型）
- [ ] 「时间范围」填同一天的起止 → 应能查到当天记录（筛选按本地时间解释）
- [ ] 填批号点「追溯全程」→ 时间正序、含该批号全程
- [ ] 「导出 Excel」→ **点一次，确认弹框、落盘、能打开**（这一步我未能自动化，是本清单里唯一没验过的界面路径）
- [ ] 导出内容与当前筛选一致

### ⚠ 第 4 步：开门相关

- [ ] 「打开可用焊丝格口」→ 记录条数**与实际开门数一致**（每个格口各一条）
- [ ] 维护视图「试开」1 格 → 产生 1 条「维护试开格口」
- [ ] 同一格口连续开关两次 → 各 1 条，条数正确

**无指令开门**（第 10 项）需要人为制造：在库内无开门指令时让某格口的锁 DI 显示释锁（拔/短接 DI 或手动解锁）。预期：记录页出现 1 条 `is_uncommanded = 1` 的记录。
> ⚠ 若锁具极性相反（DI 常态为释放），会**每把锁都判成计划外开门**。判定逻辑里「读失败/读不到」已排除，但极性不对会被判成命中。发现后告诉我，调 `DoorStateReconciler.IsUncommanded`。

### 第 5 步：失败与补偿（验收 §3 第 9 项、§3.8）

- [ ] 把 `app_operation_log` **临时改名** → 做一次存料：业务照常完成、状态栏出现写入失败告警、待补偿列表出现 1 条
- [ ] 改回表名 → 点「全部重试」→ 补写成功、记录出现、界面显示「已补写 1 条」
- [ ] 制造一次业务失败（如填一个 MES 里不存在的批号）→ 记录里 `result = 失败` 且有 `error_info`

### 第 6 步：兼容性与耗时（验收 §9）

- [ ] 跑 0.1 的五条既有演示脚本，确认功能未被影响（C2）
- [ ] 批量打开全柜格口，记录耗时（C4，建议与 0.1 对比）
- [ ] 静置 5 分钟 → 记录条数**不因轮询增长**（C5）

## 3. 预期看到、不要当故障的现象

| 现象 | 为什么 |
|---|---|
| 「MH 存入可用焊丝」的**机台号为空** | MH 存料流程里没有机台信息（存料不涉及机台）。待确认是否认可「该场景不适用」 |
| 「查看存取记录」「导出存取记录」两条留痕**操作人为空** | 记录页门禁只有密码、没有工号（§2）。已知限制 |
| 维护试开记录**只记角色** | 维护界面没有工号输入 |
| MH 批量开门记录的操作人**取决于 MH 界面工号框是否填了** | 无强制校验 |
| 格口显示「已禁用」 | `io-modules.yaml` 里模块未启用；按现场配置核对 |
| 状态栏 `RCS○` / `IO 0/4在线` | 未连接/不可达；本机与现场都要看实际配置 |

## 4. 出问题时的排查入口

| 想看什么 | 去哪 |
|---|---|
| 流程每一步实际跑的 SQL 与参数 | 把 `appsettings.json` 的 `Debug:FlowTraceWindow:Enabled` 改 true 重启 → 「流程调试 Trace」窗口 |
| 记录写入失败 | 底部状态栏告警 + 记录页「待补偿」按钮（带条数） |
| 待补偿明细 | 记录页 → 待补偿列表（入队时间 / 重试次数 / 最后错误） |
| 数据库本身 | `data/app.db`（SQLite 单文件；已开 WAL，会多出 `-wal` / `-shm` 两个附属文件，属正常） |
| 谁改了什么 | 变更说明 §3 列了对 0.1 的 4 处修正 |
