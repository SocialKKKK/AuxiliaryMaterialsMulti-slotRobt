## 2. 按风险排序的验证步骤

### ⚠ 第 1 步：MES 真库能不能通

**2026-09-29 已现场验证 Oracle 真库读写及完整作业。** 本节保留为升级后的回归检查；本次现场优先验证第 7 步的充电离站修复。

- [ ] 应用启动后底部状态栏显示 `MES✓`（不是 `MES×`）
- [ ] 走一次「MH 存入可用焊丝」：批号能查到规格、能分配格口
- [ ] 走一次「操作员存废取新」：工号能查到姓名、机台能查到产品批号

**若这一步报错**，多半是 MES 侧 SQL 的方言或数据形状问题。已做的预检：流程引用的每个 `sql_id` 在 Oracle 模式下都能解析到正式条目、11 个 mock 条目都有正式镜像（不会因缺条目断链）。所以问题会出在 SQL 内容，看流程 Trace 或日志里的 `RenderedSql` 与报错原文，改 `requirements/data-access-sql/sql-catalog/items/` 里对应条目。

### 第 2 步：记录写入（一眼可辨）

- [ ] 存料成功后打开「存取记录」页签：应有 **1 条**「MH 存入焊丝」记录，含**规格、批号、格位、时间**，以及该格的**开门时间与关门时间**（口径优化 2026-10-09：不再另有独立的开门/关门事件）
- [ ] **时间与墙上钟一致**（这条修过：库里存 UTC、界面显示本地；若显示慢 8 小时说明拿的是旧构建）
- [ ] 操作人列有「姓名(工号)」——**前提是 MH 界面的操作人工号框填了工号**（不填则该列为空，属预期）
- [ ] 走一次操作员存废取新：应产生**恰好 2 条记录**（归还 1 条、「领用并取出」1 条，两者已合并）；两条都含**门开与关门时刻**（关门确认后回填）；不应出现独立的 `door_open` / `door_close` / `op_take_wire` 成功记录

### 第 3 步：查询 / 追溯 / 导出

- [ ] 六项筛选逐个单独用一遍，再组合一次（如 时间范围 + 格口 + 动作类型）
- [ ] 「时间范围」填同一天的起止 → 应能查到当天记录（筛选按本地时间解释）
- [ ] 填批号点「追溯全程」→ 时间正序、含该批号全程
- [ ] 「导出 Excel」→ **确认文件能用 Excel 打开**（9 月 29 日已现场验证弹框、9040 B 文件落盘与导出留痕，只剩人工打开检查）
- [ ] 导出内容与当前筛选一致

### ⚠ 第 4 步：开门相关

- [ ] 「打开可用焊丝格口」→ 应产生 **N 条**「MH 取出旧焊丝」（N = 实际打开格口数，**逐格一条**）；每格关门后它自己那条的**关门时间被回填**（不新增记录）
- [ ] 维护视图「试开」1 格 → 产生 1 条「维护试开格口」
- [ ] 同一格口连续开关两次 → **2 条**「MH 取出旧焊丝」（各含自己的门开/门关时刻）

**无指令开门**（第 10 项）需要人为制造：在库内无开门指令时让某格口的锁 DI 显示释锁（拔/短接 DI 或手动解锁）。预期：记录页出现 1 条 `is_uncommanded = 1` 的记录。
> ⚠ 若锁具极性相反（DI 常态为释放），会**每把锁都判成计划外开门**。判定逻辑里「读失败/读不到」已排除，但极性不对会被判成命中。发现后告诉我，调 `DoorStateReconciler.IsUncommanded`。

### 第 5 步：失败与补偿（验收 §3 第 9 项、§3.8）

- [ ] 把 `app_operation_log` **临时改名** → 做一次存料：业务照常完成、状态栏出现写入失败告警、待补偿列表出现 **1 条**失败记录（一次存料现在只有 1 条）
- [ ] 改回表名 → 点「全部重试」→ 补写成功；记录时间仍为原动作时刻，条数与待补偿项一致
- [ ] 制造一次业务失败（如填一个 MES 里不存在的批号）→ 记录里 `result = 失败` 且有 `error_info`

### 第 6 步：兼容性与耗时（验收 §9）

### 第 7 步：AGV 控车（仓库里已有现成的场景工具）

`agv-dispatch-sdk/AgvDispatch.Sample` 是团队自带的 SDK 场景工具，**默认干跑、写接口需显式加 `--execute`**：

```bash
cd requirements/versions/0.1/wire-cabinet/agv-dispatch-sdk/AgvDispatch.Sample
# 先改它自己的 appsettings.json 里的 AgvDispatch 段（RCS 地址与车辆 deviceKey）

dotnet run -- poll           # 轮询+评估，不调写接口
dotnet run -- list           # 多车列表
dotnet run -- loop 5         # 5 次 tick，不下单
dotnet run -- all            # 依次执行，不调写接口

# 以下会产生真实动作，需显式加 --execute
dotnet run -- order <站点号> --execute
dotnet run -- pause  --execute
dotnet run -- cancel --execute
dotnet run -- charge --execute
```

- [ ] **先跑只读三连**（`poll` / `list` / `loop 5`）：验证登录鉴权、网络、状态解析与就绪判定
- [ ] 核对 **app 界面显示与 RCS 实际状态是否一致**（位置 / 电量 / 系统状态 / 订单号）
- [ ] **C5 的真实版本**：`loop` 干跑连续多轮，同时观察记录表 —— 每 5 秒轮询一台**活车**时也不应新增记录
      （本机已有静置/轮询记录验证；现场还需核对真实车辆持续轮询）
- [ ] 六条命令逐条验（**会动车**，清场 + 急停有人）：下单 → 暂停 → 继续 → 取消 → 回充 → 返航
      每条验三点：状态是否迁移、记录是否**恰好 1 条**、失败是否带 `error_info`；自动路径同一原因连续失败应合并为 1 条（`detail.count` 记次数）
- [ ] **格口联锁**（最有价值的一条）：车移动中打开任一格口 → 应自动暂停（且记录 1 条）；
      关门 → 应自动继续（再 1 条）。持续开门期间**不应反复记录**
- [ ] 产品自己的**控车 AGV 页**也点一遍（那才是交付对象；Sample 验的是 SDK 层）
- [ ] 10 月 8 日控车修复部署后：保持现场 30%/90%，充电态手动选站离站、90% 自动返航；有充电单时先请求取消、等 RCS 释放后仅下一单；门开/未知/开锁中均阻止手动和自动派车。此项必须现场放行后执行。

> ⚠ 加 `--execute` 之后命令的是**真实车辆**。先确认现场清场、急停由谁负责；
> 若 RCS 侧有测试车队或模拟车，则整节可全自动跑，先问一句。

### 第 8 步：10 月 8 日审查修复复核（5 项，本地已修、现场待验）

部署后**先做一次 catalog 自检**：打开 MES 对账页点刷新应能出列表。若提示
`柜内库存对账 SQL 条目缺失，已停止对账。`，说明 catalog 没推到位或仓库根解析不对（不是数据问题）。

- [ ] **门态未知不放行**：让某个**已接线**格口的 DI 读不到（断开模块通讯或指到不可达地址）→
      点「前往作业站」应被拒、状态栏出现 `门态未知，禁止下发移动/充电单。`
      （按钮不一定变灰，以「点后有没有真下单」为准）；恢复通讯后能正常发车
- [ ] **OP 再次点提交不得绕过关门**：归还/领用走到等关门、**门仍开着时再点一次提交** →
      只提示关门，流程与库存都不推进。这一条同时是 9 月 29 日「无指令开门」误报的**疑似根因**：
      顺带留意记录页是否还出现该误报，若出现请把时间戳一并记下
- [ ] **MES 读失败不误清**（需人工放行改库）：库存读取失败时对账应停止并提示，不写 MES、不清 `DISCOEQPNO`
- [ ] **CLEAR 只清本柜归属**：正常取出后 `DISCOEQPNO` 由本柜车名置 NULL；批号已转属他柜时（可人工构造）应拒绝清除
- [ ] **补偿并发不重复**：同一条待补偿项，人工点「重试」的同时让后台补偿也跑 → 记录表只应多 1 条

## 4. 出问题时的排查入口

| 想看什么 | 去哪 |
|---|---|
| 控车/回充异常的现场复现 | `AgvDispatch.Sample` 的 `poll` / `loop N`（干跑，不产生动作） |
