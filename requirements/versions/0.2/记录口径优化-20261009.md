# 记录口径优化（2026-10-09）

> 状态：**已实施**（2026-10-09）。需求方已确认三点：**领用与取出合并成一条**、
> **「只增不删」放宽为 A 档**（业务事实不可改写，仅允许补 NULL 门时刻 / 更新过程派生字段 detail）、
> **本轮做全量 §7 六步**。
>
> 本文改的是 0.2 §3.1「记录范围」的**口径**（粒度），不是实现缺陷修补。
> 实现见 `变更说明.md`「记录口径优化」一节；验收条款已同步到 `需求范围.md` / `验收清单.md` /
> `现场自测清单.md`。
> 触发原因：2026-10-09 现场做完一整轮 MH 存料 + OP 存废取新后，记录**可读性差、冗余严重**。

## 0. 实施结果与偏差（2026-10-09 落地后补记）

条数：一次存料 3→1；一次批量开门（53 格）159→1；一轮 OP 存废取新 7→2；
自动返航连续失败 9→1。当天 481 条 → 约 45 条量级。

与草案的四处**有意偏差**，都记在这里免得下个对话按草案找不到对应实现：

1. **`detail` 允许更新**（草案只说「只补空字段」）。口径③要求把「连续失败次数 / 首末时刻」
   累加到同一条上，这必须能改 `detail`；`detail` 是过程派生字段（格口清单、被清批号、重试统计），
   不是业务事实。触发器只放行 `detail` 这一列，其余列（谁/何时/哪个格口/哪批料/结果）仍不可改写。
2. **自动路径失败记录不加「（自动路径，重复失败已合并）」后缀**。`message` 属不可改写列，
   而记录是第一次失败就落库的（保证失败立刻可见），此刻还不知道会不会合并。次数与首末时刻改由
   `detail.count / first_ts / last_ts` 承载。
3. **`is_cleared` 在开门那一刻确定**，不在关门时。`is_cleared` 是 `NOT NULL DEFAULT 0`，
   非空值不能回填；而「开门即清空」要清的正是开门时账面已有的那批（门开着期间没人能改库存），
   所以开门时读一次库存就能定下来，语义等价。
4. **批量开门的 `door_close_ts` 取「整批都关完」的最后一次关门时刻**（与草案 §3.2 例子一致）。
   单格 / 试开则各自在关门确认时立即回填。

仍未做（留给下一轮，不属本轮 §7 范围）：**更正记录 UI**（`corrects_id` 列与「默认只看最新有效版本」
的查询投影已就位，但没有写更正记录的入口——等真出现「记录写错了」的需求再加）。


## 1. 现状量化（柜体机 `.10`，2026-10-09）

| 类别 | 动作类型 | 条数 | 占比 |
|---|---|---|---|
| 业务动作（一次人的操作） | `mh_load_available_wire` 38、`op_return_wire` 1、`op_issue_available_wire` 1、`op_take_wire` 1 | **41** | **9%** |
| 过程 / 推导 | `door_close` 150、`mh_open_slots_batch` 106、`mh_assume_empty` 106、`door_open` 40、`mh_open_slot`（误报，已修）2 | **404** | **84%** |
| 控车 | `agv_move` 28、`agv_charge` 4 | 32 | 6% |
| 查看留痕 | `view_operation_log` | 4 | 1% |

当天现场只做了 **40 次人的动作**（38 盘存料 + 2 次批量开门清场）另加 1 轮 OP，却写出 **481 条**记录——
**平均 1 次人的动作 ≈ 12 条记录**。全库（9/29 起，9624 条）里 `agv_move` 4333 条（45%）、
门事件与批量/清空约 3360 条，真正的业务记录（`mh_load` + `op_*`）只有约 970 条。

典型冗余：

- **一次 MH 存料 = 3 条**（`door_open` + `door_close` + `mh_load_available_wire`），
  而开门/关门时刻在业务记录里**已经有两个字段**（`door_open_ts` / `door_close_ts`）——同一个时刻被记三遍。
- **一次批量开门 = 3×N 条**（逐格开门 + 逐格关门 + 逐格「开门即清空」）。现场早上开 53 格 = **159 条**，人为动作只有 1 个。
- **自动路径失败重复记账**：同一原因每 3 秒失败一次各记一条（现场 15:07–15:08 一段就是十几条）。
- 误报类记录（如 10/09 的假「计划外开门」）**只能再追加记录来纠正**，越纠越多——见 §4。

## 2. 新口径

> **一次「人的操作 / 有业务意义的动作」= 一条记录；开门、关门、清空是这条记录上的字段。
> 只有当一次开门没有产生任何业务记录时（维护试开、物理/无指令开门、流程中断放弃），
> 才单独留门事件记录。**

这条规则同时满足「查得到」（一条记录带全 谁/何时/哪个格口/哪批料/结果/门时刻）与「看得懂」（不再一屏全是门与清空）。
它不是新加约束——`需求范围.md` §3.1 设计说明里本来就有**「一次业务操作记一条」**这条原则，
现在的逐格/逐事件展开反而是为了门事件破的例，本次是**回归该原则**。

### 动作类型去留

| 处理 | 动作类型 |
|---|---|
| **保留为独立记录**（一动作一条） | `mh_load_available_wire`、`op_return_wire`、`op_issue_available_wire`、`op_take_wire`、`agv_move`、`agv_charge`、`maint_trial_open`、`view_operation_log`、`export_operation_log` |
| **合并成一条** | `mh_open_slots_batch`：一次批量开门 1 条，带格口清单与数量 |
| **降级为字段**（字段均已存在） | `door_open`/`door_close` → 业务记录的 `door_open_ts`/`door_close_ts`；`mh_assume_empty` → `is_cleared` + 被清批号 |
| **仅在异常时独立保留** | 无业务结果的门事件；`uncommanded_open` 计划外开门（`is_uncommanded=1`） |
| **合并记账** | 自动路径（自动返航/自动回充/轮询）**同一原因连续失败** → 1 条 + 次数 + 首/末时刻；人工操作失败仍逐条记 |

新增字段（**只加列，不动历史**，现有"只增不删"用例已放行 `ALTER ADD COLUMN`）：
`detail`（TEXT/JSON：格口清单、清空批号、重试统计）、`slot_count`。

## 4. 「只增不删」的收敛（A/B/C）

现状约束：`OperationLogRetentionTests` 用正则扫全部 SQL catalog + 产品源码，禁止
`UPDATE app_operation_log` / `DELETE FROM app_operation_log`（允许 `ALTER ADD COLUMN`，并带反空转自检）。

判断：**原则对（发生过的业务事实不可抹掉或悄悄改写），但"整行任何时候都不能动"过头了**，有三处代价：

1. **后到的信息填不进去**——无指令开门/维护试开在开门时就写了记录，关门时刻后到却无法回填，
   只能再写一条配对记录。**约束自己在制造冗余**（业务记录在关门后写，所以不受影响）。
2. **错误记录只能靠"再加一条"纠正**——10/09 的假「计划外开门」就是例子，错的记录还在，越纠越多。
3. **表内没有生命周期标记**——无法表达"已归档"，表只能无限长大。

建议改成「**业务事实不可改写**」：

| 档 | 允许 | 仍禁止 | 强制方式 |
|---|---|---|---|
| 现在 | INSERT、ALTER 加列 | 任何 UPDATE / DELETE | 正则扫 SQL+源码（保留） |
| **A（建议）** | **只补空字段**：`SET door_close_ts=? WHERE id=? AND door_close_ts IS NULL` | 改任何已有值 | 正则改**白名单**（只放行该模式）；更稳是库层加 `BEFORE UPDATE` 触发器（旧值非 NULL 或改到非白名单列即 `RAISE(ABORT)`） |
| **B（建议一起做）** | **更正记录**：新增 `corrects_id` 指向被更正记录；查询默认取最新有效版本 | 原地改事实字段 | 同 A；查询层做投影 |
| **C（可选）** | **归档标记** `archived_at` + 明细落归档库/文件（归档本身仍只增） | 物理删行 | 只写标记列 |

优先级：**冗余主因是口径不是约束**——先做 §2 口径（481→约 45），再放宽 A/B（只解决"后到信息"与"纠错"）。
不要把"允许 UPDATE"当成解决冗余的手段。

补充：现约束给的是**心理保证**（防代码写错），不是密码学保证（DBA 可直接改库）。
真需要"可证明未被篡改"应上**哈希链**（每条带前一条哈希 + 定期外部留存），对产线追溯场景**过重**，不建议。

## 5. 需要改的需求条款

- §3.1 第 9 项「开门和关门分别追加一条」→ **并入业务记录的 `door_open_ts`/`door_close_ts`；无业务结果时才独立成条**。
- §3.1 第 6 项「每个成功开门的格口各记 1 条」→ **一次批量动作 1 条 + 格口清单**。
- §3.1 第 11 项「开门即清空」单列为动作类型 → **降级为 `is_cleared` 字段**（字段已存在）。
- §3.1 第 8 项 控车 → **自动路径重复失败合并记账**。
- §3.1 设计说明「一次业务操作记一条」→ **提升为总口径**，删除与之冲突的逐条例外。
- **验收口径同步改**：`验收清单.md` / `现场自测清单.md` 里「另有开门、关门事件」「应产生恰好 3 条业务记录，另外有归还门、领用门的开关事件」这类断言，要改成"一条业务记录带门时刻"。**这是验收标准的变更，须需求方一并确认**，否则现场自测会按旧清单判失败。

### 实施前查明的两个事实（2026-10-09，柜体机实测）

1. **业务记录现在大多不带门时刻**：当天 38 条 `mh_load_available_wire`、`op_return_wire`、`op_issue_available_wire` 的 `door_open_ts`/`door_close_ts` **都是 NULL**，只有 `op_take_wire` 带（它的节点 `updateIssueSlotAfterUnload` 在关门之后执行，能读到 runtime 里的两个时刻）。所以"停写门事件"必须先让业务记录带上门时刻，否则信息就真丢了。
2. **归还 / 领用是"先记账、后开关门"**：`op_return_wire` 写于 `submitWireReturn`（与开门同秒、早于关门），`op_issue_available_wire` 写于 `submitWireIssue`——**写记录时门还没开**，拿不到门时刻。因此这两类有两条路线：

   | 路线 | 做法 | 代价 |
   |---|---|---|
   | **① 改时机** | 把该半程的业务记录移到"关门确认"之后再写（引擎侧调整节点记账时机，不改流程 YAML） | 中途放弃就没记录，需补一条"未完成/失败"记录；且记录语义变成"完成后才算" |
   | **② 保持现时机 + 补字段（建议）** | 提交时照常写记录（`结果=成功`、门时刻 NULL），关门后**只补空字段**把门时刻回填 | **依赖 §4 的 A 档**；好处是"未完成"一眼可见（门时刻为 NULL），且不动记账时机、风险低 |

   **建议路线 ②**，理由：它正是 §4 A 档的第一个真实用途（后到的信息就该能补），且不会因为"中途放弃"而丢掉记录。存料（`updateDB` 在关门之后）不属于这一类，可以按路线 ① 天然成立——只需把门时刻带上。
